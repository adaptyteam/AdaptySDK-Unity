# The SDK harness

`Assets/SdkHarness/` is a scene with nothing in it but `AdaptySdkHarness`, which registers four `[CliCommand]`s in the player: `harness_activate`, `harness_call` (any public static `Adapty` or `AdaptyUI` method by name, arguments as a JSON object keyed by parameter name, the overload chosen by exactly that key set — an argument written as `"$GetFlow"` or `"$GetPaywallProducts[0]"` is the object the last successful call of that method handed back, which is how a flow reaches `GetPaywallProducts` and a product reaches `MakePurchase`; do not paste a returned model's JSON back instead, the SDK never reads a response model from JSON — a product goes out as `AdaptyPaywallProductRequest`, its own shape — so the dump has no reader and fails on the subscription offer while proving nothing), `harness_events` (what the listeners received, decoded), `harness_status`. It exists because the desktop suite feeds the SDK fixtures, and only a player can say whether the C# layer decodes what the *native* SDK actually returns, on IL2CPP, after stripping — which is why the harness build adds a link.xml of its own (`SdkHarnessBuild`, not a file under `Assets/`, which would go into the demo's and `StrippingBuild`'s players too) that keeps only what the harness reaches by reflection — `Adapty`'s and `AdaptyUI`'s methods, `AdaptyJson`, the request-side types it builds from JSON or by member name — and leaves the response models and converters to the linker; a new request-side parameter type goes on that list. A callback with a value-type payload (`bool`, an enum) needs no AOT hint: IL2CPP's full generic sharing runs the `Capture<T>` the harness makes at run time. Commands run on the request thread and post the call to the main one, because the SDK delivers callbacks through `SynchronizationContext.Post` and a main-thread wait would deadlock every call; the wait budget (`--timeout_ms`, 20 s by default) stays under the runtime server's 120 s request timeout (`requestTimeoutMs` in `RuntimePipelineConfig.json`); the first calls after an activation with a customer id have taken 8–20 s while the backend merged the profile, so give those more. It does not expose the raw bridge JSON — the request/response bytes live inside `AdaptyRequest` — only what the SDK decoded. It activates once per process: relaunch the app for another activation. The scenario is data, not code, so a new test is a new payload and needs no rebuild. The screen is not empty for the person watching: a UI Toolkit ledger built in code (the only asset is `SdkHarnessPanel.asset` with its `unity-theme://default` theme) lists every request (→), reply (←), failure (×), late reply (← or × with "late" — the command already returned as timed out; the object still becomes the handle) and delivered event («) with its timestamp, so a run can be followed on the simulator and read back when the agent is stuck.

## Build and run

Build it with its own `harness_build` command (`Assets/SdkHarness/Editor/`), not `unity command build`: the CLI sends a single `--scenes` value as a string, the server binds that to an empty array and silently builds `EditorBuildSettings` instead, and `dry_run` reports a nonexistent scene as valid. A player build holds the main thread for minutes, so submit it detached and wait on the job:
```bash
unity command harness_build --detach                          # scenes = Assets/SdkHarness/SdkHarness.unity, iOS, Development, SimulatorSDK
unity job wait <job-id> --timeout 1500
xcrun simctl uninstall <udid> com.adapty.adaptydemoapp      # or the previous install's descriptor passes for readiness
osascript -e 'tell application "Xcode"
  set ws to open "'"$PWD"'/ios-harness-build/Unity-iPhone.xcworkspace"
  repeat until loaded of ws
    delay 1
  end repeat
  set active scheme of ws to (first scheme of ws whose name is "Unity-iPhone")
  set active run destination of ws to (first run destination of ws whose name is "iPhone 17 Pro (26.5)")
  run ws
end tell'
APP=$(xcrun simctl get_app_container <udid> com.adapty.adaptydemoapp app)   # --runtime-path takes this DIRECTORY, not the descriptor file inside it
unity command harness_activate --runtime-path "$APP"
unity command harness_call --runtime-path "$APP" --method GetFlow --args '{"placementId":"rt.RegTestPaywall1","fetchPolicy":"Default","loadTimeout":10}'
```

Open the **workspace**: External Dependency Manager writes a Podfile, and the bare `.xcodeproj` fails at link with `framework 'Pods_UnityFramework' not found`. Xcode runs it, not `xcodebuild`, because of purchases: `harness_build` files `Assets/SdkHarness/AdaptyDemo.storekit` in the project (as `text`, with no target membership — Xcode offers nothing else as a configuration) and selects it in the scheme's Run options, and Xcode syncs that configuration into the simulator through its Instruments service when it launches the app, so `storekitd` serves the products locally and `MakePurchase` raises Xcode's confirmation sheet instead of the Apple Account sign-in. Nothing else performs that sync: `xcodebuild` (build or test) ignores the scheme option, and an `SKTestSession` opened from the app, or from an `xcodebuild test` host, is refused by `storekitd` as not entitled. Xcode names its destination by device and runtime (`iPhone 17 Pro (26.5)`) and boots that simulator even when another one is up, so address the device by UDID (`xcrun simctl list devices`) rather than `booted`. The sheet and the "You're all set" alert after it take a tap each; the `ios-storekit-purchase` skill (`.claude/skills/ios-storekit-purchase/`) says which log line means which window is up and where its button is, so a purchase needs no screenshot. On the harness that is: `harness_activate`, `GetFlow` and `GetPaywallProducts` first, then `harness_call --method MakePurchase --args '{"product":"$GetPaywallProducts[0]"}' --timeout_ms 90000` in the background — it returns only after the alert's OK — and `GetProfile` to see the access level. The descriptor with the port and token appears next to the app's `Data/` once the server is up, which makes its existence the readiness signal.

## Commitment billing plans

`AdaptyDemo.storekit` carries one product on a commitment plan: `yearly.commitment.6999`, in a group of its own, billed up front at 69.99 or monthly at 6.99 over a 12-month commitment (83.88). No placement offers it, so a run builds the flow by hand: take `GetFlow`'s result, set `variations[0].products[0].vendor_product_id` to `yearly.commitment.6999` and its `pricing_terms` to `[{"billing_plan_id":"monthly"}]`, and pass that JSON as `GetPaywallProducts {"flow": …}` — a flow, unlike a product, has a JSON reader. `MakePurchase` with the result raises the commitment sheet ("$6.99 per month, 12-month commitment"), and the access level in the purchase result carries `billing_plan_id: "monthly"` and `commitment` 1 of 12. Renewals are not observable this way: iOS maps a renewed transaction to an access level through the backend's product list, which has no such product.

The format is the one Xcode 26.6 and the iOS 26.5 runtime accept, found by trial: `version` 5.0 (4.0 has no billing plans), `billingPlanType` `BILLED_UPFRONT` and `MONTHLY` (Xcode's editor spells them `upfront`/`monthly`, `storekitd` rejects those), and the up-front plan listed too — a product with only the monthly plan loads but is never returned. Xcode re-encodes the file into the simulator as `Data/Containers/Shared/AppGroup/<id>/Documents/Persistence/Octane/<bundle>/Configuration.storekit`, and `storekitd` reads that copy: a config it cannot read leaves every product unresolved, and the reason is in the simulator log as `Failed to read StoreKit configuration data`, not in Xcode. Local StoreKit reports such a product's `price` as the monthly amount with the commitment's `displayPrice` ($83.88), in both the product price and `commitment_info.price`; the SDK passes both through as StoreKit gives them.

## What the commands can and cannot take

Some argument shapes have no JSON reader in the SDK and get one in the harness: a type whose instances are public static members (`AdaptyPlacementFetchPolicy`, `AdaptyExternalAttributionProvider`) is addressed by member name, and a string for a type with a one-string constructor becomes that instance (a provider by identifier); a `TimeSpan` parameter is taken as seconds (inside an object it is Newtonsoft's `"00:00:10"`); an `IReadOnlyList<T>` parameter is read element by element by the same rules, so `ShowStoreMessages` takes `{"iosFilter":["BillingIssue","storekit_-42"]}`; enums go through the SDK's own converter as strings; a request-only model with a nested `Builder` (`AdaptyProfileParameters`, `AdaptyConfiguration`) is built from a JSON object — constructor arguments by parameter name, every other key a `Set<Key>` call, `customAttributes` an object of string or number values — so `UpdateProfile` takes `{"param":{"firstName":"A","customAttributes":{"plan":"pro","score":3}}}`. Models with public fields and a parameterless constructor (`AdaptyUICreateFlowViewParameters`, `AdaptyUIDialogConfiguration`, `AdaptyPurchaseParameters`) read as plain JSON. Not reachable this way: `AdaptyCustomAsset` values (factory methods, no members), custom tags and timers on `CreateFlowView` (setters, not fields), `SetFallback` (needs a file in the app), and the legacy onboarding events (`IAdaptyOnboardingsEventsListener` is obsolete; the harness does not register it). `Activate` is refused by `harness_call` because activation is once per process — `harness_activate` builds the configuration, with `--configuration` for the Builder keys it has no flag for. `harness_build` targets the iOS simulator SDK and `harness_build_android` an Android device (see below). The player's own command set adds `console`, `runtime_status`, `simulate_pointer`; `eval` is registered there but compiled out on anything that is not the Editor or a standalone development build, which is why the harness's commands are compiled ones. An iOS device is out of reach without a package change: the runtime server writes its descriptor into the app bundle and stops itself when that write fails.

## Android

`harness_build_android` (`Assets/SdkHarness/Editor/`) builds the same scene into `android-harness-build.apk`: Development, ARM64, `com.adaptytest`. Both harness builds set `EditorUserBuildSettings.development`, because the Pipeline build processor reads that flag rather than the build options, and with Enable In Builds on it stops an interactive build on a Continue / Cancel / Disable Pipeline dialog that nothing driving the Editor from the CLI can answer. Pipeline 0.6.0 starts the runtime server from Project Settings > Pipeline > Runtime (`ProjectSettings/Packages/com.unity.pipeline/RuntimePipelineConfig.json`, `enableInBuilds` on, port 7900), not from a scene component — the package no longer has the `RuntimePipelineManager` the scene used to carry.

The stock runtime server cannot run on a device: it writes its descriptor next to `Application.dataPath`, which on Android is the APK, the write throws and the server stops itself. `AndroidHarnessServer` (`Assets/SdkHarness/AndroidHarnessServer.cs`, `UNITY_ANDROID` only) turns the driver's autostart off at `AfterSceneLoad` and runs a subclass that writes the descriptor into the app's internal files directory, with a token of its own since the package's token manager is internal. Reaching it from the host:
```bash
adb install -r android-harness-build.apk && adb shell monkey -p com.adaptytest -c android.intent.category.LAUNCHER 1
adb shell run-as com.adaptytest cat files/.unity-pipeline-runtime-port > rt/.unity-pipeline-runtime-port   # a Development build is debuggable
adb forward tcp:7900 tcp:7900
unity command harness_status --runtime-path rt
```
Two things the CLI checks on the pulled copy, and deletes it when they fail: `pid` has to be a live process of the current user on the host (the device pid is meaningless here, and pid 1 is refused) — rewrite it to a long-lived one such as the Hub's; and `lastHeartbeat` has to be recent — rewrite it before each command, the device server does not touch its file on heartbeats. The Editor's Android Logcat restarts the adb server, which drops the forward: re-add it before each command too. `adb shell input tap`/`keyevent` do reach the flow.

A flow is an Activity of its own on Android, and Unity's player loop is paused underneath it: `harness_call` (a post to the main thread) times out until the flow is gone, `harness_events` still answers. The SDK's callbacks are delivered through the Unity thread's native looper, which keeps running through the pause, so a `flow_view_did_perform_action` for Back or close shows up in `harness_events` within seconds — that is the check that the bridge delivers while paused, and it is what the demo app relies on to dismiss the view on close. The harness itself dismisses nothing: bring `UnityPlayerActivity` back with `am start -f 0x20000000`, which ends the flow and resumes the loop.

A purchase on a device goes to Google Play for real, so the account on the device has to be a license tester on a track `com.adaptytest` is published to — otherwise `MakePurchase` fails at once with `StoreProductNotAvailable` (Play's `ITEM_UNAVAILABLE`) and no sheet; a tester's sheet says "Test card, always approves", and a test subscription renews every five minutes. The sheet pauses the player loop like a flow does, so call `MakePurchase` with a short `--timeout_ms` and read the outcome from `GetProfile` once `UnityPlayerActivity` is back on top (`adb shell dumpsys activity activities | grep topResumedActivity`). Play's Subscribe button ignores injected touches — `input tap` on it does nothing while the rest of the sheet takes taps — but not keys: send `input keyevent KEYCODE_TAB` one at a time, `uiautomator dump` after each until the button's node is `focused="true"`, then `KEYCODE_ENTER`. On Xiaomi, `adb` input needs Developer options > USB debugging (Security settings) and an `adb reconnect` after it, installing needs Install via USB, and MIUI may kill the harness behind the sheet, which leaves the purchase unfinished: relaunch, pull the descriptor again and activate. A subscription the account already owns raises no sheet, so let a test one lapse or take another product; the test app's paywalls carry subscriptions only.
